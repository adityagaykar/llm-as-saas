Design an LLM-as-a-Service platform
that serves frontier models at global scale

This is the "Design the Claude / OpenAI API" interview question. You need to show that you understand the parts that are specific to LLMs, such as memory-bound decoding, the KV cache, batching, model parallelism, and token-based quotas, as well as the usual SaaS parts like authentication, rate limiting, metering, multi-region failover, and observability.

Disclaimer: Anthropic, OpenAI and Google do not publish parameter counts or internal serving architecture. Every model size on this page is an illustrative assumption picked to make the math concrete. "GPT Astra" is treated as a hypothetical next-generation frontier model. The architecture uses publicly documented industry techniques (continuous batching, PagedAttention, prefix caching, prefill/decode disaggregation, MoE expert parallelism, speculative decoding, FP8/FP4 quantization) and publicly announced facts, such as Anthropic running on a mix of AWS Trainium, Google TPU and NVIDIA GPUs and offering prompt caching and a discounted Batch API.

The one insight that drives the whole design

Prefill is compute-bound

All prompt tokens are processed in parallel as large matrix multiplications, so the GPU runs at high utilization. Cost scales with 2 × active_params × prompt_tokens FLOPs. This phase determines time-to-first-token (TTFT).

Decode is memory-bandwidth-bound

Each new token needs a full read of the (active) weights plus the sequence's KV cache from HBM, and it produces only one token per sequence. The fix is to batch many sequences so they share one weight read. Batch size is limited by KV-cache memory and by the per-token latency SLO (TPOT).

"Serving LLMs efficiently comes down to keeping expensive accelerators saturated without breaking latency SLOs. Decode is memory-bandwidth-bound, so I raise throughput by batching more sequences per weight read. That makes KV-cache memory the scarce resource, so most of my design decisions (paged KV, prefix caching, quantization, prefill/decode disaggregation, routing) aim to fit more useful sequences into HBM and keep the batch full."

3.Requirements

Functional

  • Text generation from a messages/chat payload (system prompt, multi-turn, images/PDFs).
  • Streaming token output (SSE) and non-streaming responses.
  • Model selection by name/version (e.g. claude-opus-x, -sonnet-x) with pinned versions and aliases.
  • Tool use / function calling, structured (JSON) output, stop sequences, sampling params.
  • Prompt caching: reuse a shared prefix at a discount and with lower latency.
  • Batch API: asynchronous large jobs at lower price (results within 24h).
  • Token counting endpoint; usage reported per request.
  • Org / workspace / API-key management, usage dashboards, billing.
  • Per-org rate limits and spend limits by tier.

Non-functional

  • Latency: TTFT p50 < 0.5–1s, p99 < 3–5s for typical prompts. TPOT (time per output token) 15–60 ms by tier.
  • Availability: 99.9%+ for API. Graceful degradation under overload.
  • Throughput / efficiency: maximize goodput (tokens/s that meet SLO) per accelerator. The main cost driver is accelerator-hours.
  • Scalability: 10× traffic growth per year. New larger models every few months.
  • Fairness & isolation: one tenant cannot starve others. Priority classes.
  • Security & privacy: TLS everywhere, tenant isolation of caches, encryption at rest, configurable retention.
  • Safety: abuse detection, usage-policy classifiers, auditability.
  • Correctness: accurate token metering (billing). At-least-once usage events with idempotent aggregation.
  • Observability: per-model, per-region, per-tenant SLO dashboards.

4.Model tiers and what each one needs

All numbers are assumptions for interview math. Frontier models are generally believed to be sparse Mixture-of-Experts (MoE): total parameters set the memory footprint, while active parameters per token set compute and bandwidth per token.

How to read this: "Min accelerators" = enough HBM for the weights with ~40% left for KV cache. In practice you deploy more than the minimum, because extra HBM means a bigger batch, which raises throughput per dollar, and because aggregate memory bandwidth lowers TPOT. The larger the model, the more the serving unit grows from one GPU, to one node, to one rack-scale NVLink/ICI domain, to multiple racks.

5.Back-of-envelope calculations

Core formulas (memorize these)

Weights memory        = total_params × bytes_per_param          (BF16=2, FP8=1, FP4=0.5)
KV cache per token    = 2 (K and V) × layers × kv_heads × head_dim × bytes
KV per sequence       = KV_per_token × (prompt_tokens + output_tokens)
Max concurrent seqs   = (HBM_total − weights − activations) / KV_per_sequence

FLOPs per token       ≈ 2 × active_params                       (forward pass)
Prefill time          ≈ 2 × active_params × prompt_tokens / (N × peak_FLOPs × MFU)
Decode step time      ≈ max( bytes_read / (N × HBM_BW),   2 × active_params × batch / (N × FLOPs) ) + comm
      bytes_read      = weights_touched + batch × KV_per_token × avg_context
Per-user tok/s        = 1 / step_time                           (TPOT = step_time)
Replica tok/s         = batch / step_time
Replicas needed       = peak_output_tok_s / replica_tok_s
Concurrency (Little)  = peak_QPS × (TTFT + output_tokens × TPOT)
$ per 1M out tokens   = replica_$_per_hour / (replica_tok_s × 3600) × 1e6

Worked example: Opus 5.5-class (assumed 3T total / 200B active MoE, FP8)

1. Traffic

  • 10M DAU × 10 requests/day = 100M req/day
  • ÷ 86,400 ≈ 1,160 QPS avg. Peak 3× ≈ 3,500 QPS
  • Prompt 3,000 tokens (50% cache hit), output 400 tokens
  • Peak output ≈ 3,500 × 400 = 1.4M tok/s
  • Peak uncached input ≈ 3,500 × 1,500 = 5.2M tok/s

2. Memory per replica

  • Weights: 3T × 1 B = 3 TB. That needs at least 16 × 192 GB GPUs just for weights
  • Choose a 36-GPU (288 GB) rack-scale domain: ~9.3 TB usable, so ~6.3 TB for KV
  • KV/token = 2 × 120 layers × 8 kv_heads × 128 × 1 B ≈ 240 KB
  • 3.4K-token sequence ≈ 0.8 GB. A 200K-token sequence ≈ 49 GB, which is why long context is expensive

3. Decode speed

  • Aggregate BW = 36 × 8 TB/s × 70% ≈ 200 TB/s
  • Batch 256: weights touched ≈ 3 TB + KV read ≈ 0.2 TB, about 3.2 TB per step
  • Step ≈ 16 ms + ~3.5 ms comm ≈ ~20 ms TPOT (~50 tok/s per user)
  • Replica throughput ≈ 256 / 0.02 ≈ ~13K tok/s
  • Compute check: 2 × 200B × 256 = 0.1 PFLOP per step, well under capacity. Memory-bound, confirmed

4. Fleet & cost

  • Decode: 1.4M / 13K ≈ ~110 replicas × 36 ≈ 4,000 GPUs
  • Prefill: 5.2M tok/s × 2 × 200B ≈ 2.1 EFLOP/s ÷ (5 PF × 40%) ≈ ~1,050 GPUs
  • Total ~5K GPUs, at ~1.8 kW all-in × 1.3 PUE ≈ ~12 MW for this one tier
  • Cost per 1M output tokens ≈ (36 × $7/h) / (13K × 3600 / 1e6) ≈ ~$5 (at full utilization)
"Weights alone are about 3 TB, so the serving unit has to be a rack-scale NVLink domain and not a single 8-GPU node. Decode is memory-bound: each step reads about 3 TB across about 200 TB/s of aggregate bandwidth, which is roughly 16 ms. With a batch of 256 I get about 13K tokens/s per replica at about 50 tokens/s per user. Peak output demand of 1.4M tokens/s therefore needs about 110 replicas. The biggest levers on that number are batch size, which is bounded by KV memory and TPOT, quantization, and prefix-cache hit rate."

    Design notes

    • SSE over HTTP/1.1 or HTTP/2: one-directional, works through proxies, easy to resume or close. WebSockets are only needed for bidirectional real-time use such as voice.
    • Rate-limit headers: x-ratelimit-remaining-tokens, retry-after.

    • Idempotency: generation is not idempotent. Support a request-id for dedupe of billing and for client retries.
    • Usage block always returned. It is the source of truth for client-side cost tracking.

    9.Low-level design: deep dives

    9.1 Inference engine: continuous batching

    Problem with static batching

    Requests finish at different lengths. With static batching, slots that finish early sit idle until the longest sequence completes, and new requests wait.

    Iteration-level (continuous) batching

    The scheduler runs every decode step. It removes finished sequences, admits waiting ones if KV blocks are free, and runs one forward pass for the whole batch. This gives 2–10× throughput over static batching.

    Engine loop (pseudo-code)

    while True:
  finished = [s for s in running if s.done()]
  free_kv_blocks(finished); stream_final(finished)
  # admit new work within KV + token budget
  while waiting and kv.can_alloc(waiting[0]) \
        and step_tokens < TOKEN_BUDGET:
      seq = waiting.pop_by_priority()
      seq.prefix_hit = prefix_cache.match(seq)
      running.add(seq)          # prefill in chunks
  batch = build(running, chunked_prefill=True)
  logits = model.forward(batch)  # CUDA graph / XLA
  tokens = sample(logits, params, grammar_masks)
  emit(tokens); maybe_preempt_if_kv_full()

    Chunked prefill splits long prompts into chunks (e.g. 512–2K tokens) that are mixed into decode batches, so a 100K-token prompt does not stall every other user's TPOT. Preemption: when KV runs out, evict the lowest-priority sequence by swapping its KV to host DRAM or recomputing it later.

    9.2 KV-cache management: PagedAttention and prefix caching

    Paged KV

    • KV stored in fixed-size blocks (e.g. 16–64 tokens). Each sequence has a block table (logical to physical), like OS virtual memory.
    • Near-zero fragmentation, so more concurrent sequences fit, so batches are larger.
    • Copy-on-write sharing for parallel sampling (n > 1) and beam search.

    Prefix (prompt) caching

    • Hash each full block, chained with the hash of the previous block, to get a radix tree of cached prefixes.
    • A new request walks the tree and reuses matched blocks, so it only prefills the suffix.
    • Agentic and coding workloads resend long, mostly identical histories, so hit rates can be very high. This cuts TTFT and prefill cost.
    • Productized as explicit cache breakpoints with a TTL (e.g. 5 min default, longer option). Cache writes are billed at a premium and cache reads at a steep discount.
    • Security: cache keys are scoped by org, so there is no cross-tenant reuse or timing side-channel.

    9.4 Prefill / decode disaggregation

    flowchart LR R["Scheduler"] --> P1["Prefill replica A
    high MFU, big chunks"] R --> P2["Prefill replica B"] P1 -- "KV blocks via RDMA" --> D1["Decode replica 1
    large batch, high MBU"] P2 -- "KV blocks via RDMA" --> D2["Decode replica 2"] P1 -.-> D2 D1 --> O["Token stream"] D2 --> O

    Why

    • Prefill and decode interfere: a big prefill stalls decode steps and causes TPOT spikes.
    • They have different optimal configs (parallelism, batch, even hardware generation).
    • You can scale them independently: the P:D ratio follows the input:output token mix (RAG/agents are prefill-heavy).

    Costs / when not to

    • KV transfer: 3K tokens × 240 KB ≈ 0.7 GB. Over 400 Gb/s RDMA that is about 15 ms, which is acceptable. Use layer-wise pipelined transfer.
    • Needs a fast fabric and more operational complexity.
    • For small models or low load, colocated + chunked prefill is simpler and good enough.

    9.5 Decode speedups

    Speculative decoding

    A cheap draft (small model, n-gram, or built-in multi-token-prediction heads) proposes k tokens. The big model verifies them in one pass. Output distribution is unchanged. Gives 1.5–3× lower TPOT when the acceptance rate is high (code, structured text).

    Quantization

    FP8 weights and activations are now standard. FP4 (MX/NV formats) on newer hardware. Halving bytes per parameter roughly halves memory-bound decode time and doubles KV room. Must pass eval gates for quality regressions.

    KV compression

    GQA/MQA or latent attention (MLA) cut KV per token by 4–30×. FP8 KV gives another 2×. Sliding-window or hybrid attention layers help long context.

    Kernels & runtime

    FlashAttention-style fused kernels, CUDA graphs / XLA compilation to remove launch overhead, overlapped comm and compute, and fused MoE grouped GEMM.

    Structured output

    Grammar-constrained decoding (JSON schema to token masks) computed on CPU and overlapped with the GPU step.

    Expert load balancing

    Replicate hot experts, and periodically rebalance placement from observed routing statistics.

    9.6 Routing & scheduling

    Cache-aware load balancing

    • Key = hash(org_id, first N prefix blocks). Use consistent hashing with bounded load, so the same conversation lands on the replica holding its KV.
    • Score = α·prefix_match_len − β·queue_depth − γ·KV_utilization. Pick the best of k candidates (power of k choices).
    • Spill to another replica if the preferred one is hot. Accept a cache miss rather than queueing.

    Priority & fairness

    • Classes: interactive paid > interactive free > batch API > internal/offline.
    • Weighted fair queuing by org inside each class, so one tenant cannot monopolize a pool.
    • Batch jobs fill diurnal troughs, which raises average utilization (hence the batch discount).
    • Deadline-aware: shed from the queue if the expected wait already blows the TTFT SLO.

    9.7 Rate limiting by tokens

    On request:
  est_in  = tokenize(prompt)             # exact, at gateway
  reserve = est_in (ITPM bucket) + max_tokens (OTPM bucket) + 1 (RPM bucket)
  if any bucket lacks capacity -> 429 with retry-after
On completion:
  refund OTPM bucket by (max_tokens - actual_output)
Implementation:
  Redis Lua script for atomic multi-bucket check (sharded by org_id)
  + per-gateway local leaky-bucket cache to absorb bursts; reconcile every ~100ms
  cache-read tokens count less (or not at all) toward ITPM -> incentivizes caching

    9.8 Autoscaling & weight distribution

    • Cold start is slow: 3 TB of weights at ~25 GB/s per node from object storage takes minutes. Mitigations: pre-stage weights on local NVMe, use peer-to-peer (BitTorrent-style) broadcast inside the cluster, GPU-direct storage, and keep warm standby replicas.
    • Scaling signals: queue depth, KV-cache utilization, TTFT p95, tokens/s. Do not use CPU%.
    • Capacity is reserved, not elastic: frontier accelerators are bought or leased long-term. Autoscaling mostly reassigns fixed capacity between model tiers, batch vs interactive, and research vs prod. Forecast diurnal and weekly patterns.
    • Heterogeneous fleet: one model version is compiled per hardware target (GPU / TPU / Trainium). The router treats them as interchangeable pools, with per-pool throughput weights.

    9.10 Safety, security, observability

    Safety

    • Lightweight input classifiers inline (small model, low latency).
    • Streaming output classifiers that can halt generation.
    • Async abuse detection on usage patterns.

    Security

    • Keys hashed (never stored raw). mTLS internally.
    • Tenant-scoped caches. HBM/KV is zeroed or reused only within its tenant scope.
    • Weights encrypted at rest. Restricted access to serving nodes.

    Observability

    • TTFT, TPOT, queue time, goodput per model, region and tier.
    • KV utilization, batch size, MBU/MFU, expert load skew.
    • 429/529 rates, stream disconnects, accelerator health (ECC, XID errors).

    10.Scaling each tier efficiently

    As models grow, the serving unit grows and the dominant bottleneck moves: compute/overhead, then KV capacity, then HBM bandwidth, then interconnect, then power and cold start.

    Small Haiku-class

    • Fits on one accelerator, so scale with pure data parallelism and simple least-loaded routing.
    • Batches are cheap, so run very large batches. The bottleneck becomes CPU-side scheduling, tokenization and sampling. Use CUDA graphs and an async scheduler.
    • Can run on older or cheaper hardware (previous-gen GPUs, inference chips).
    • Also used internally as speculative-draft model, safety classifier and router.

    Mid Sonnet-class

    • Single 4–8 accelerator node: TP/EP inside NVLink. Many replicas, and the largest fleet by tokens.
    • Coding agents drive long, repeated contexts, so prefix caching + cache-aware routing is the main efficiency lever (often >50% of input tokens are cache reads).
    • KV capacity limits batch size, so use FP8 KV and offload to host DRAM.
    • Disaggregate P/D once the traffic mix is prefill-heavy.

    Large Opus 4.4-class

    • Weights exceed one node, so 2+ nodes (16+ GPUs) or rack-scale domains with wide EP.
    • P/D disaggregation pays off: prefill on compute-dense nodes, decode with large batches on high-HBM nodes.
    • Speculative decoding to bring TPOT back to acceptable interactive speed.
    • Fewer, larger replicas, so replica failure has a bigger blast radius. Keep N+2 spare per region.

    Frontier Opus 5.5-class

    • Rack-scale serving unit (e.g. 72-GPU NVLink domain, TPU pod slice, Trainium UltraServer). The all-to-all for EP stays inside the domain.
    • FP8 weights (FP4 where quality allows) and MTP-based speculative decoding.
    • Long context (200K–1M): context parallelism for prefill, and KV offload/compression for decode. Price long context higher.
    • Capacity spread across clouds and accelerator types. The global router balances them.

    Hypothetical GPT Astra-class

    • Multi-trillion MoE that may exceed one rack, so PP across racks + EP within rack, with micro-batching to hide pipeline bubbles.
    • FP4 weights, aggressive KV compression, and possibly hybrid attention.
    • Power-bound: tens of MW per region, so siting decisions follow power availability.
    • Launch with admission gating (waitlists, tier-based access, lower rate limits) until capacity ramps.
    • Weight distribution becomes a first-class system (multi-TB per replica × hundreds of replicas).

    Fleet-level levers (all tiers)

    • Diurnal sharing: shift accelerators between interactive and batch/research by time of day.
    • Model cascades: product-side routing of easy tasks to smaller models (never silently. Model choice is the customer's).
    • Multi-region: follow-the-sun capacity. Data-residency pins some tenants.
    • Hardware heterogeneity: use each generation where it is most cost-effective (older GPUs for small models or prefill).

    12.Key trade-offs to articulate

    Batch size: throughput vs latency

    Bigger batch lowers $/token but raises TPOT. Choose the largest batch that meets the TPOT SLO. Offer different SLO tiers, such as a "fast mode" at a higher price that runs smaller batches or more GPUs per replica.

    More GPUs per replica

    More aggregate bandwidth gives lower TPOT and more KV room, but adds communication overhead and a larger blast radius. There is a sweet spot per model.

    Quantization

    About 2× efficiency per halving of precision, at the risk of quality loss. It must be validated on evals per model.

    Cache affinity vs load balance

    Sticky routing raises hit rate but creates hotspots. Bounded-load consistent hashing gives you both.

    Colocated vs disaggregated P/D

    Disaggregation gives SLO isolation and independent scaling, at the cost of KV-transfer bandwidth and complexity.

    Fail-open vs fail-closed

    Availability vs quota enforcement. Choose per control (rate limits fail open, spend caps fail closed).

    13.Common follow-up questions (with crisp answers)

    Why is decode memory-bound, and why does batching help?

    Each decode step reads all active weights from HBM to produce one token per sequence. Arithmetic intensity is about 2 FLOPs per byte per sequence, far below the roughly 300+ FLOPs/byte needed to saturate modern accelerators. Batching B sequences reuses the same weight read for B tokens, so intensity scales with B until KV reads or compute dominate.

    How do you choose batch size?

    Take the largest B such that (a) the KV for all B sequences fits in free HBM and (b) step time stays under the TPOT SLO. Make it dynamic: the engine admits work under a token budget, and the scheduler preempts when KV is exhausted.

    A user sends a 1M-token prompt. What happens?

    Check quota (it counts against ITPM). Route to a long-context pool. Prefill with context parallelism and chunking so it doesn't stall others. KV is about 240 GB at 240 KB/token, which is a large slice of a replica, so long-context requests get their own pool and pricing. Prompt caching is critical for repeated long documents.

    How does prompt caching work end to end, and why is it cheaper?

    The client marks cache breakpoints. The engine hashes blocks of the prefix (scoped to the org) and stores KV in HBM, spilling to DRAM/SSD with a TTL. A later request with the same prefix skips prefill for matched blocks, which saves compute (FLOPs ∝ tokens) and TTFT. Writes are priced higher because they consume memory. Reads are cheaper because they skip compute. The router must be cache-aware for hits to happen.

    A GPU dies while 300 users are streaming. What happens?

    The replica is marked unhealthy and its streams terminate. The gateway either sends an error event (clients retry with the conversation so far) or transparently re-submits prompt + generated tokens to a healthy replica. Re-prefill is fast thanks to prefix cache or because prefill is cheap relative to decode. The replica is drained and rebuilt from a warm spare.

    How would you cut cost per token by 2×?

    (1) FP8 to FP4 weights/KV where quality holds. (2) Raise prefix-cache hit rate via cache-aware routing. (3) Speculative decoding or MTP. (4) Larger batches via KV compression or offload. (5) Fill troughs with batch traffic to raise utilization. (6) P/D disaggregation to right-size each phase. (7) Better kernels and comm overlap (MBU 60% to 80%).

    How do you roll out a new model (e.g. Opus 4.4 to 5.5)?

    Pre-stage weights across regions. Compile per hardware target. Load-test to find batch/TPOT curves. Shadow traffic, then internal dogfood, then gradual % rollout behind a new model id (customers opt in by name, and aliases move later). Reallocate capacity from the old tier progressively. Keep the old version serving for pinned customers until deprecation.

    429 vs 529: who is at fault?

    429 means the customer exceeded their rate limit. 529/503 means the provider is out of capacity. Both carry retry-after. Clients use exponential backoff with jitter. Server-side, shed lowest-priority classes first.

    How do you keep rate limits consistent across regions?

    Give each region a share of the global budget (periodically rebalanced by observed demand) and enforce it locally in Redis. Exact global consistency isn't worth cross-region latency on every request. A small over-admit is acceptable for rate limits, but not for hard spend caps, which are reconciled more strictly.

    Why MoE, and what does it change for serving?

    MoE gives the quality of a huge model at the per-token compute of a much smaller one. But all experts must stay in memory, the all-to-all communication needs a high-bandwidth domain, and expert load imbalance creates stragglers. At large batch nearly every expert is touched each step, so decode reads close to the full weights.

    Is output deterministic at temperature 0?

    Not guaranteed. Batch composition changes reduction order in floating-point kernels, and MoE routing ties can flip. Determinism requires batch-invariant kernels, which cost some throughput.

    Numbers (approximate)

    • NVLink (H100) ~900 GB/s, (Blackwell) ~1.8 TB/s per GPU. InfiniBand/Ethernet NIC 400–800 Gb/s (50–100 GB/s).

    • FLOPs/token ≈ 2 × active params. Prefill ~ compute-bound. Decode ~ bandwidth-bound.
    • Read 1 TB at 100 TB/s = 10 ms, so that is your TPOT floor.
